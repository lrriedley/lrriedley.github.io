Git Workflow

The branching, review, and release process I designed for Night District's engineering team, from a feature branch to production.

The dev branch always contains stable, deployable code. Protection rules on the GitHub repository restrict direct commits to it.

1. Git Pull

First, pull to get the latest version of dev.

git pull

2. Branching

Before making changes, create a branch off dev. Branch names start with one of the following categories, followed by a slash and a camelCase description:

  • feat/feature-name — for adding a new feature
  • fix/what-was-fixed — for fixing a bug
  • change/what-was-changed — for making a minor change
  • test/testing-for-what — for adding a new test
  • design/what-was-designed — for altering a design

For instance, a branch for adding user authentication could be feat/user-authentication. All work happens inside these feature branches. 

git checkout -b <feat/branch-name>

3. Initial Pull Request

Immediately after creating the branch, push it to the remote for full transparency and early feedback. The PR name matches the branch name. 

git push origin <feature-branch>

4. Committing

When ready to commit, review what's changed:

git status

Stage changed files:

git add path/to/file

Commit with short statements describing the changes, separated by semicolons and written in order: 

git commit -m 'add new button component; add new button components to templates'
git commit -m 'add the stop directive to button component to prevent propagation'

5. Push

Before pushing, check whether dev has moved:

git checkout dev
git status

If dev has new commits, merge it into the feature branch and resolve any conflicts:

git checkout <feature-branch>
git merge dev

Then push:

git push origin <feature-branch>

6. Complete Pull Request

PRs are concise and focused on a particular change, bug fix, or feature.
Keep it neat, keep it sweet — like a perfect cocktail 🍸
  • Create the PR in GitHub, named after the branch.
  • Write a descriptive PR description summarizing what changed.
  • Add reviewers.
  • Tests run automatically once the PR is submitted.
  • If tests pass, a manager reviews the code.

7. Merging

Once reviewed and approved, a manager merges the PR into dev using Squash and merge, then deletes the feature branch.

8. Pull & Delete Branch

After the merge, switch to dev, pull the change down, and delete the local branch:

git checkout dev
git pull
git branch -D <branch-name>

Promoting dev into staging

git switch staging
git pull
git checkout -B merge/dev-into-staging
git merge dev

Resolve conflicts if needed, then push:

git push --set-upstream origin merge/dev-into-staging

Open a PR named merge/dev-into-staging into staging, add reviewers, and wait on the build and tests. Once a manager approves, the PR merges into dev using Create a merge commit, and the merge branch is deleted.

Promoting staging into main

git switch main
git pull
git checkout -B merge/staging-into-main
git merge staging

Resolve conflicts if needed, then push:

git push --set-upstream origin merge/staging-into-main

Open a PR named merge/staging-into-main into main, add reviewers, and wait on the build and tests. Once a manager approves, the PR merges using Create a merge commit, and the merge branch is deleted.
